# NX2Apple : emplacements Mac et séparation Jeux / Fabrique

Recherche statique, 4 novembre 2026. **Aucun déplacement, lancement, build ou test effectué.** La release [v1.1.0](https://github.com/LNPANDY/NX2Apple/releases/tag/v1.1.0) pointe sur le commit `2f788d6b55192952dfacaf97f24700d7668610b6`, distinct des fichiers pré-téléchargés au commit `8d13135e2a1eec10406f6b486157ec1d2f56eafd`. Les passages déterminants ont été recoupés sur le tag v1.1.0 ; les liens ci-dessous visent le tag ou, explicitement, le commit téléchargé. Aucun comportement à l'exécution n'est affirmé comme testé.

**Conclusion pratique :** le dossier de bibliothèque est un périmètre de découverte, pas un déménagement. Le choix du dossier de sortie lie par défaut l'app finale **et** le cache de build : l'interface ne garantit donc pas à elle seule une séparation stricte A/B. Les jeux existants peuvent être détectés et lancés sans reconstruction d'après le code ; leur comportement de sauvegarde dépend du moteur déjà embarqué dans chaque `.app`.

## Apps déjà construites et premier Play

**Vérifié dans le code.** Une recherche parcourt le dossier choisi jusqu'à une profondeur limitée, au plus 4 000 répertoires, en sautant divers dossiers techniques ; elle cherche aussi au premier niveau de `/Applications` et `~/Applications`. L'app doit présenter un `DMTitleID` hexadécimal à 16 caractères et deux exécutables : celui de `CFBundleExecutable` et `dmhost`. Les apps reconnues sont associées par title ID, sans copie. Une app déjà reconnue et encore prête reste prioritaire, même si une autre copie est trouvée. Voir [Library.swift:262-285,358-398,490-534](https://github.com/LNPANDY/NX2Apple/blob/8d13135e2a1eec10406f6b486157ec1d2f56eafd/frontend/Sources/NX2Apple/Library.swift#L262-L285), et la [version v1.1.0](https://github.com/LNPANDY/NX2Apple/blob/v1.1.0/frontend/Sources/NX2Apple/Library.swift).

Le fichier `Contents/Resources/dm/launcher.json` est lu pour les options offertes, **pas comme condition de reconnaissance** ; son absence limite les options lues. Les préférences persistantes sont partagées avec le launcher natif si le binaire sait les lire ; pour des versions anciennes, NX2Apple transmet les choix en variables d'environnement. Voir [Library.swift:127-138](https://github.com/LNPANDY/NX2Apple/blob/8d13135e2a1eec10406f6b486157ec1d2f56eafd/frontend/Sources/NX2Apple/Library.swift#L127-L138) et [SavedChoices.swift:122-151](https://github.com/LNPANDY/NX2Apple/blob/8d13135e2a1eec10406f6b486157ec1d2f56eafd/frontend/Sources/NX2Apple/SavedChoices.swift#L122-L151).

La note de release dit que les anciens jeux sont reconstruits au premier Play. **Mais le code Mac v1.1.0 contredit une interprétation universelle** : `primaryAction` ouvre directement une `.app` valide ; sinon il ouvre la configuration de build. Il ne vérifie pas la chaîne ni ne démarre un build dans ce chemin. Voir [LauncherView.swift:590-620](https://github.com/LNPANDY/NX2Apple/blob/v1.1.0/frontend/Sources/NX2Apple/LauncherView.swift#L590-L620). La traduction de l'interface dit plutôt recompilation des shaders **à la prochaine compilation** : [fr.json:475](https://github.com/LNPANDY/NX2Apple/blob/v1.1.0/frontend/l10n/fr.json#L475). Une entrée importée sans build enregistré a en outre `toolsCommit` vide ; son âge n'est donc pas établi par cette métadonnée.

**Déduit, non testé :** les apps de `apps/` décrites dans le contexte devraient être reconnues si leurs `Info.plist` et permissions remplissent les critères ; les ouvrir via Play devrait éviter une reconstruction, comme les ouvrir par Finder. Cela conserve aussi leur ancien moteur et ne procure pas les améliorations de v1.1.0. Une compilation ultérieure avec une chaîne différente peut reconstruire les shaders : conserver les caches ne garantit pas leur réutilisation. On ne peut pas garantir ici le fonctionnement réel ou l'absence d'autres effets au lancement. Les sidecars `*.app.key` sont des empreintes de packaging, pas des clés Nintendo ; les conserver avec les apps si l'ancien flux doit rester utilisable ([README local:264-270](../../README.md#L264-L270)).

## Sauvegardes, mods et risques

**Vérifié :** le marqueur `.nx2apple-library` ne modifie pas une app construite hors NX2Apple : le code doit déjà être dans son exécutable. Pour une app construite avec le patch, le marqueur doit être dans le **parent immédiat de cette app**, pas simplement dans la racine de recherche. Le premier lancement copie les anciennes sauvegardes uniquement si la destination est vide ; les originaux restent. Une copie partielle ou des sauvegardes divergentes exigent une vérification avant toute bascule : le code ne fusionne pas deux dossiers non vides. `env.txt` et les caches runtime restent sous `~/Library`. [Patch v1.1.0:90-107](https://github.com/LNPANDY/NX2Apple/blob/v1.1.0/patches/0010-mac-library-folder.patch#L90-L107).

Les mods NX2Apple sont des remplacements RomFS ; les mods exclusivement `exefs` ne sont pas utilisables par ce mécanisme. Ils ne sont passés que par le lancement NX2Apple : Finder ne reçoit pas automatiquement cet environnement. Des cheats ont un mécanisme distinct (`DM_CHEATS`) ; les annonces v1.1.0 sur `mods` et `env.txt` **par jeu dans le dossier partagé concernent iPhone/iPad**, pas une promesse équivalente sur Mac. [Library.swift:203-235](https://github.com/LNPANDY/NX2Apple/blob/8d13135e2a1eec10406f6b486157ec1d2f56eafd/frontend/Sources/NX2Apple/Library.swift#L203-L235), [frontends.md local:90](../../source/docs/frontends.md#L90), [release v1.1.0](https://github.com/LNPANDY/NX2Apple/releases/tag/v1.1.0).

- **Chemins absolus :** l'index garde notamment app, sources, sortie et illustrations. Déplacer une arborescence ne réécrit pas automatiquement tous ces chemins ; un rescan peut retrouver l'app mais ne remplace pas forcément les anciennes entrées non vides. Le lien actuel `keys/prod.keys` pointe vers un original dans Downloads : ne pas supprimer cet original ([README local:96-98](../../README.md#L96-L98)). Préserver aussi le clone `source/` et son patch local.
- **Disque externe :** le code conserve les chemins d'apps sur un volume `/Volumes/<nom>` non monté, mais les efface si le volume est monté et le fichier absent ; l'app est indisponible tant que le disque est débranché ([Library.swift:319-340](https://github.com/LNPANDY/NX2Apple/blob/8d13135e2a1eec10406f6b486157ec1d2f56eafd/frontend/Sources/NX2Apple/Library.swift#L319-L340)). Pour une sauvegarde déplacée manuellement, APFS est important : les transactions utilisent clone et échange atomique ([services.md local:166](../../source/docs/reference/services.md#L166)). Ne pas supposer une reprise sûre après débranchement pendant l'écriture.
- **iCloud :** la synchronisation est distincte du répertoire de sauvegarde active ; vérifier les conflits et les copies de secours avant changement. Le build refuse un dossier de travail détecté comme cloud ([v1.1.0 BuildStore+Run.swift:80-86](https://github.com/LNPANDY/NX2Apple/blob/v1.1.0/frontend/Sources/NXModel/BuildStore%2BRun.swift#L80-L86)). La release dit que le déplacement du cache vers un disque externe n'a pas été testé sur appareil.
- **Séparation stricte :** construire dans B, puis envisager séparément la publication de l'app et de ses sidecars vers A ; c'est une proposition, pas une procédure validée. Pour une app NX2Apple patchée, accompagner l'app de son marqueur et des sauvegardes appropriées ; vérifier les chemins et les copies sans écraser une sauvegarde. Aucun déplacement n'est autorisé par ce rapport.

**Non trouvé :** réglage indépendant du cache de build Mac, du magasin moteur de la release, de `library.json`, ou de la racine complète `env.txt`/sauvegardes locales ; preuve que tous les binaires déjà présents embarquent exactement le code du checkout actuel ; essai réel de découverte, lancement, synchronisation ou migration.
